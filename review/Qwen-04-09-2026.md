Field data sanitised per `field_tests/FIELDTEST.MD`.

## SECTION 1 — Executive Summary

**Project summary.** Network Recon Engine is a read-only SSH diagnostics collector whose stated objective is: *point at one device, receive a complete troubleshooting package for the relevant infrastructure*. It has completed 53+ phased iterations under a four-role AI SDLC (Claude architect → Kimi implementer → GPT/Terra reviewer → field evidence via Qwen-scoped research), building: multi-vendor command profiles, device identity/role detection, CDP/LLDP topology graph, graph traversal with checkpoint/resume, bounded parallel collection, health scoring, AI-ready bundles, an EDR-compatible embedded-Python portable distribution, build provenance capture, and a platform-specific ArubaOS-CX profile validated to 9/10 commands on real hardware.

**Overall verdict in one line:** the project's *process* is unusually disciplined and evidence-driven, but its *default execution path* currently cannot silently deliver the primary objective on the only platform it has field-validated, and several core capabilities (traversal expansion, cross-platform neighbor parsing, meaningful health scoring) remain unproven anywhere.

**Top 5 decisions (from DDR):**

1. **DD-008 — provenance artifact with full stored patch** (PHASE-035): the single highest-leverage governance decision; directly enabled catching the PHASE-048 stale-build failure. Watch item: it degrades to `head_commit_sha: "unknown"` inside packaged builds (verified in both field bundles), which is exactly where field runs happen.
2. **DD-012 — platform-aware profile selection** (PHASE-047): delivered the only field-verified capability win (9/10 → expected 10/10 on ArubaOS-CX). Watch item: wired into only one of two collectors (see Section 8).
3. **DD-015 — unbounded `allowed_devices=None` in the parallel collector** (PHASE-053): corrects DD-014's rejected implementation and restores the one-device-to-package objective. Watch item: the behaviour it enables is unfield-tested (PHASE-054 not implemented).
4. **DD-006 — opt-in legacy KEX profile**: pragmatic, evidence-sourced response to legacy SSH peers; contained blast radius.
5. **DD-014 — Rejected** (PHASE-052): worth listing because the *rejection itself* was the decision that delivered value — it prevented shipping a default path that could never meet the objective, and demonstrates the review gate actually bites.

**Top 5 risks (full register in Section 7):**

1. Silent generic-profile execution on the now-default recursive path (field-proven, `docs/Phases` + `field_tests/output2.zip`).
2. Topology discovery silently fails on the only field-validated platform (ArubaOS-CX LLDP format doesn't match the parser regexes) — traversal cannot expand, degrading the primary objective to single-device collection with no warning.
3. Two divergent collection engines: the parallel path drops the entire evidence/recovery contract and platform-aware selection.
4. Field evidence unattributable in packaged builds (`head_commit_sha: "unknown"`) + current `dist/` appears built from an uncommitted tree (zip predates the commit containing its code).
5. Misleading health scoring (Cisco-centric normalisation → `health_score: 100, warnings: []` on bundles with failed commands, verified in both field bundles).

## SECTION 2 — Current State Assessment

**Solving the right problem?** Yes. Read-only, engineer-facing, "stop SSH'ing into fifty devices" is a real and bounded problem, and the safety constraint (blocklist + allowlist validation, `vendor_profiles.py:6-45`) is the right foundation for a tool that will be pointed at production networks with shared credentials.

**Does the feature set support the primary objective?** Partially, and not yet along the default path:

- **Works, field-proven:** single-device ArubaOS-CX collection via the flat/interactive path (9/10 commands; the 10th fixed in PHASE-051 pending re-validation); portable distribution surviving Defender ASR; provenance emission; bundle packaging.
- **Broken or unproven on the default path:** identity detection is skipped entirely when recursion is active (the default since PHASE-052/053, `app/cli.py:246-268`), platform-aware selection never engages there, and neighbor discovery parses zero neighbors from ArubaOS-CX output (`app/discovery.py:47-68` vs. the actual captured LLDP format). The tool therefore completes "successfully" (`status: partial`, `health_score: 100`) while silently failing the objective.
- **Unproven anywhere:** multi-hop traversal over real edges, checkpoint resume on real runs, parallel collection against real devices, FortiGate support (a traversal-supported vendor with **no command profile** — `app/classification.py:6-11` enqueues `fortigate` neighbors, `VENDOR_PROFILES` has no `fortigate` key, so they silently collect the generic `show` set against a FortiOS CLI), Cisco/Juniper/Arista profiles on real hardware.

**Highest real-world value delivered so far:**
1. **Portable distribution + interactive launch** (PHASE-021→024, 022 chain): the difference between a repo and a tool a field engineer can actually run on a managed endpoint. Two EDR-forced pivots show genuine field adaptation.
2. **Field-evidence loop itself** (PHASE-030→039, DD-007/DD-008/DD-009): per-command failure evidence and provenance turned opaque field failures into root-causeable data.
3. **ArubaOS-CX profile correction** (PHASE-046→051): the first evidenced platform-specific correctness, 5/10 → 9/10.

**Limited value so far:**
- **Health scoring** as shipped: three Cisco-centric thresholds over normalised fields; produces 100/empty on every observed Aruba bundle including those with failed commands. Currently a false-comfort feature.
- **Parallel scoped collection** (asyncssh): cannot run on the only validated platform (no neighbors discovered), drops the evidence contract, and was built before the traversal it accelerates was proven. Capability ahead of need.
- **AI prompt/bundle**: generic by design, fine as packaging, but adds little until profiles/normalisation are multi-vendor-real.

**Most beneficial workstreams:** distribution portability; evidence/provenance instrumentation; ArubaOS-CX profile remediation. Least beneficial per effort: the credential-placeholder validation chain (PHASE-042→044, three phases for `${VAR}` robustness — correct but low operational leverage) and repeated documentation-only remediations.

**Documentation drift (new finding):** README still states "Omitting `--recursive` performs a flat, non-recursive collection" (README.md:153) — the opposite of current behaviour (recursion default, `--recursive` a no-op alias, `app/cli.py:69-74, 246-248`). This project's own review once rejected a phase for exactly this class of drift (PHASE-020).

## SECTION 3 — Architecture Assessment

**Discovery architecture (CDP/LLDP → neighbors):** *Most fragile component.* `extract_neighbors()` matches command names containing `cdp`/`lldp` then applies Cisco-format regexes (`Device ID:`, `IP address:`, `Chassis id:`, `System Name:` — `app/discovery.py:27-66`). The captured ArubaOS-CX output uses `Neighbor System-Name`, `Neighbor Chassis-ID`, `Neighbor Management-Address` — zero matches (8 real neighbors including one with a management IP sat in the o1 bundle while `discovered_neighbors: []`). Even with regex fixes, `classify_neighbor_support()` requires vendor markers in platform/capability strings that ArubaOS-CX doesn't emit, and the IP-extraction logic expects a chassis-ID IP rather than a management address. **No field evidence exists that neighbor discovery works on any platform.**

**Traversal architecture:** Mature in design (graph BFS, visited/pending/failed/unsupported sets, cycle safety, checkpoint filtering — `app/orchestrator.py`, `app/parallel_collector.py:138-274`), and the PHASE-017 A/B and 052→053 sequence shows the state-leak defects were hunted down layer by layer. But it is mature *only where tested*: every traversal behaviour beyond "collect the seed" has only synthetic-test evidence. Unbounded default expansion is capped at `max_devices=100` with no confirmation, no hop cap, and default credentials reused for every discovered neighbor — a real AAA/credential blast radius once discovery works.

**Profile architecture:** Sound two-level model (vendor → optional role; platform overlay per DD-012) with deterministic read-only validation. Weaknesses: (a) **silent generic fallback** for unknown/auto vendor keys (`app/vendor_profiles.py:153-156`) — the defect that masked the field anomaly; (b) platform selection wired into `app/collector.py:52-53` only; `app/parallel_collector.py:90` omits `platform` (explicitly accepted deviation in PHASE-047); (c) FortiGate traversable but profile-less; (d) profiles are single-firmware snapshots (DD-013 honestly says so).

**Evidence architecture:** The project's best engineering. Per-command elapsed/error-type/partial-output, channel/transport state snapshots, recovery tracking (`app/collector.py:125-146`), all serialized through summary → troubleshooting bundle → ZIP — after three remediation rounds (PHASE-030→031, 036→037, 038) that prove the team learns. Critical weakness: **this contract applies to the sequential Paramiko path only**. The parallel collector captures none of it (no `failed_command_details`, no recovery, `exit_status == 0` success rule, `ERROR: stderr` raw files — `app/parallel_collector.py:102-135`), a gap recorded since PHASE-031 and still open.

**Provenance architecture (DD-008):** Conceptually excellent and proven decisively useful (PHASE-048 exposure). Two verified gaps: packaged builds have no git, so artifacts record `unknown`/`dirty:"false"` (both PHASE-050 bundles, `app/provenance.py:57-60`); staged/untracked files remain outside the patch (review-of-review accepted as limitation). Net effect: the very runs that matter (packaged field runs) are unattributable.

**Platform detection architecture:** String heuristics over one `show version` probe (`app/detector.py:15-45`) — adequate for PoC, correctly confidence-scored. Two issues: detection **exists only in the non-recursive CLI branch** (`app/cli.py:269-316`), and heuristics produce false positives (o1 recorded `model: "2017-2023"` from a copyright line via `detector.py:27`).

**Most mature:** evidence instrumentation, checkpoint/scope state management, the DDR/phase process itself. **Most fragile:** neighbor discovery/parsing, cross-path consistency (three distinct device-handling behaviours: flat/sequential/parallel), packaged-build provenance.

**Scaling concerns:** modest for the intended use (fault-domain collection, ≤100 devices). The real scaling issue is organisational: every vendor/platform adds an unbounded tail of parsing formats for discovery, normalisation, and health — none of which is abstracted yet; each will be bespoke regex work, as the Aruba case demonstrates.

## SECTION 4 — Field Validation Assessment

**Major lessons field testing revealed:**
1. **Managed endpoints decide your distribution architecture.** SentinelOne deleted the onefile exe; Defender ASR Rule `01443614…` blocked low-prevalence exe; forced two pivots ending in embedded-CPython + script launchers (PHASE-021→024). Field evidence correctly overrode architecture.
2. **Command failures are vendor-syntax, not transport, until proven otherwise** (PHASE-046: 5 parser rejections, zero transport error types).
3. **Timeouts cascade into dead-session failures, but the device-side root cause remained unresolved** (PHASE-032/034: death-at-timeout disproven, death-after supported, causation inconclusive; retry also timed out).
4. **Field runs and committed code drift apart** — twice (PHASE-034 fingerprint-only; PHASE-048 tested a build that never contained the fix).
5. **The flat path works and the default path silently doesn't** (PHASE-050 output1 vs output2, this review's special investigation).
6. Copied virtualenvs break across machines (PHASE-016 origin); real credentials leak into repos (PHASE-041 origin).

**Assumptions disproven:** generic Aruba profile ≈ ArubaOS-CX; PyInstaller exes run on managed estates; diff fingerprints are sufficient proof of build state; session-death-at-timeout; single-hop scoping satisfies the vision's own 3-hop example; (implicitly) detection-once-at-CLI is sufficient once recursion became default.

**Assumptions still unverified:** neighbor parsing on *any* real platform; traversal expansion, cycle handling, and checkpoint resume on live networks; parallel collection on live devices; FortiGate/Juniper/Cisco/Arista profiles on real devices; health thresholds; running-config completeness; that a single default credential set works across discovered neighbors; `show logging` on hardware (PHASE-051 fix untested).

**How effectively does the project learn?** Genuinely well above baseline: every field anomaly spawned a bounded phase; blocked outcomes were documented honestly rather than fabricated (PHASE-040/046/048); a review-of-review mechanism corrected reviewer overreach (PHASE-035). **But learning is gated on hardware access**: three validation phases ended "inconclusive — no reachable device," and the project has one reachable platform (ArubaOS-CX), creating single-vendor tunnel-vision risk.

**Where field evidence is influencing design correctly:** distribution model, ArubaOS-CX profile, timeout-evidence/recovery instrumentation, provenance requirements, validation gating (PHASE-049/054 prep-before-field phases).

**Where field evidence is underutilised:** the output2 generic-profile anomaly was observed, sits in `field_tests/`, but was **never written up in any committed phase/FieldEvidence document** and did not drive a phase; the empty `discovered_neighbors` beside 11KB of LLDP output was not flagged; health-score-100-with-failures was never questioned; REVIEW-PHASE-050's "short running-config" candidate phase was deprioritised behind traversal changes.

## SECTION 5 — SDLC Assessment

**Workflow:** Claude (architect, phase selection, DDR creation) → Kimi (implement, propose DDR) → GPT/Terra (approve/reject, DDR authority, push gate) with Qwen-scoped research/validation and field evidence feeding back.

**Strengths (evidenced, not assumed):**
- **Real separation of powers with teeth:** DD-014 rejected *after* implementation; DD-010 rejected twice; four consecutive 022-series rejections each found a strictly deeper defect; push withheld (DO NOT PUSH with reasons) repeatedly; a reviewer's own rejection was overturned by REVIEW-OF-REVIEW when it exceeded the phase contract. This is a functioning adversarial loop, not ceremony.
- **Traceability** via Phase/Implemented/Review artefacts + journal deltas is unusually complete; carried risks are propagated verbatim across reviews.
- **Change budget** (≤10 files/≤1000 lines) demonstrably forces decomposition; remediation phases are small and reviewable.
- **Evidence-first culture:** field-validation phases exist as first-class phases with explicit blocked outcomes.

**Weaknesses/risks:**
- **DDR authority leaks:** journal shows Kimi "Approved DD-010" (2026-09-03) and "Updated DD-012 status from Proposed to Approved" (2026-09-04); approval belongs to the reviewer. DD-012 has no REVIEW-PHASE-047 file at all. Traceability of the single most important platform decision is incomplete.
- **Review depth is bounded by token economy:** 300-token review caps work for deltas but correlate with the recurring class of miss — *acceptance-level behaviour untested while unit tests are green* ("tests pass despite both critical acceptance failures", REVIEW-PHASE-022). No reviewer or test ever asserted identity detection on the recursive path, or LLDP parsing against a real ArubaOS-CX sample.
- **Cross-path consistency is nobody's job:** the flat/sequential vs parallel divergence (evidence contract, platform param) has been recorded as "outstanding" since PHASE-031 without an owner.
- **Artefact gaps in the Aruba chain:** no REVIEW-PHASE-047; PHASE-050 exists only as a review; the decisive output2 anomaly undocumented.
- **Blind spots:** single human owner operates all roles through prompt files — review independence is model-level, not organisational; no automated CI gate (tests are run by agents' self-report, which once proved unreproducible — PHASE-022C); field access is a single point of failure.

## SECTION 8 — Investigation Priorities & Special Investigation

### Special investigation: Generic profile used despite Aruba-CX capability

**Established facts (verified first-hand):**
- Same packaged build, same device, minutes apart (04/09 ~13:31Z vs ~13:37Z): flat interactive run detected `vendor=aruba, platform=arubaos-cx` and executed the 10-command aruba-cx profile (9/10 accepted); `--recursive` interactive run recorded `vendor: "auto", platform: "unknown", identity_confidence: 0.0`, executed exactly the 5 generic commands, with `show interfaces` / `show system uptime` rejected by the device parser; its console shows **no** probe and **no** `Detected identity` line.
- Source trace: recursion (default since PHASE-052/053) routes through `_run_recursive_cli()` → orchestrator → `execute_device_collection()` with unpopulated metadata; `get_vendor_commands("auto", …)` falls silently to generic.

**Assessment of the four candidate causes:**
1. **Profile-selection defect — CONTRIBUTING, confirmed at code level.** The silent fallback for unknown vendor keys (`app/vendor_profiles.py:153-156`) is the mechanism that converts the upstream gap into wrong commands with no warning. Not the root cause by itself.
2. **Platform metadata propagation defect — NOT the primary cause here** (the metadata wasn't lost in transit; it was never produced on that path). *However*, a genuine propagation defect exists latently: `app/parallel_collector.py:90` never passes `platform`, so even a correctly identified aruba device on the `--target-device` path would get generic-aruba, not aruba-cx.
3. **Alternate execution-path defect — ROOT CAUSE (highest confidence).** Identity detection is wired only into the non-recursive branch (`app/cli.py:269-316`); the recursive path — now the default user journey — never probes or identifies. Evidence: console transcript, summary identity fields, code path.
4. **Build/runtime mismatch — DISPROVEN for this incident.** The identical build minutes earlier selected aruba-cx on the same device. Note however that *attribution* of that build is itself unverifiable (`head_commit_sha: "unknown"`; dist built from an uncommitted tree), which is risk #4, not this incident's cause.

**Priority: highest in the project.** This is not an edge case: since PHASE-052/053, *the default path is the broken path*. Every future field test run through default recursion will re-collect wrong commands and wrong topology, poisoning the evidence loop itself. PHASE-054's traversal field test would, as currently designed, mostly re-prove this defect rather than test traversal.

**Project risk level: High.** **Impact on future field testing:** until fixed, all field evidence gathered via default recursion must be treated as suspect; traversal-expansion validation specifically cannot conclude, because zero neighbors will ever be discovered on ArubaOS-CX regardless of the traversal fix.

### Next 3 investigations
1. **Default-path identity & selection audit** (above): prove/fix detection + platform-aware selection on recursive/parallel paths; make unknown-vendor fallback a loud, recorded warning event (aligns with the Qwen-prompt "generic fallback analysis" question: treat "no supported profile" as an evidence event, not silence).
2. **ArubaOS-CX neighbor-discovery format study**: capture `show lldp neighbor-info detail` (and check `show cdp` applicability) against documented formats; determine the minimal parsing + classification changes (System-Name/Chassis-ID/Management-Address mapping, capability→vendor inference) needed for the first real edge to appear in `topology.json`.
3. **Build attribution for packaged runtimes**: how can a packaged build carry a commit SHA + content hash (build-time stamping into `app/` or `run_portable.py`) so `build_provenance.json` stops saying `unknown` — prerequisite for trusting any field bundle, including retrodicting the current dist.

## SECTION 10 — Recommendations

**Now (before any further field testing):**
1. Fix the default path: perform identity detection on recursive/parallel paths (or centralise it inside the collectors), pass `platform` in `parallel_collector`, and replace the silent generic fallback with an explicit warning + recorded evidence field. Add one integration test per execution path asserting detection→profile-selection→command-set.
2. Execute PHASE-054 as defined, plus stamp packaged builds with the commit SHA/content hash so provenance is attributable outside git.
3. Correct README/HOWTO to the post-PHASE-052/053 defaults (and audit all docs for the same drift).

**Soon:**
4. ArubaOS-CX LLDP parsing + classification remediation — the smallest change that could produce the project's first real topology edge and unlock the primary objective.
5. Extend the evidence contract to the parallel collector (`failed_command_details`, recovery fields, stdout preservation) or explicitly DDR-defer it with an acceptance gate that parallel results are "provisional evidence."
6. Make health scoring honest: emit a warning/penalty for `failed_commands` and `status: partial` regardless of normalisation coverage; mark un-normalised platforms as "unscored" rather than 100.
7. Close the credential-history and running-config handling threads (authorised rotation decision; documented bundle-redaction/handling guidance beyond FIELDTEST policy).

**Guardrails:**
8. A standing DDR/traceability rule the implementer may never set `Status: Approved`; missing review artefacts block phase closure (would have caught REVIEW-PHASE-047's absence).
9. Require field findings to be written up in `docs/FieldEvidence` before the next phase selection (output2's anomaly is currently institutional amnesia).

## SECTION 11 — What NRE Is Doing Well

- **Evidence-driven development is real**: field anomalies → bounded phases → honest blocked outcomes; no fabricated validation anywhere in the record.
- **A review gate with genuine veto power** (DD-014, DD-010 ×2, four-round 022 chain, review-of-review) — rare even in human SDLCs.
- **Safety engineering** (read-only enforcement, concurrency ceiling, scoped parallelism) designed in, not bolted on.
- **Provenance as a first-class concept** (DD-008) — and it already paid for itself once.
- **Adaptability under real constraints**: two EDR-forced distribution pivots absorbed cleanly; embedded-CPython bundle is the right answer.
- **Remediation discipline**: defects get narrow, testable fix phases, not rewrites (016B restoration, 017A/B, 026A/B, 053).

## SECTION 12 — What NRE Is Most Likely To Get Wrong Next

1. **Field-testing PHASE-054's traversal defaults on the recursive path without first fixing identity/profile selection** — yielding another inconclusive or misleading evidence round (the o2 anomaly, repeated by design).
2. **Declaring traversal "working" from synthetic tests or single-node field runs** while neighbor parsing silently returns zero on real output formats.
3. **Letting `health_score: 100` and `status: partial` coexist into engineer-facing reports**, eroding trust the first time a 100-scored bundle turns out to be the wrong command set.
4. **Another uncommitted-tree "quick" field build** (the pattern has recurred three times).
5. **Expanding to more vendors/commands before the first two-hop field topology exists** — growing the unvalidated surface instead of proving the core loop.

## SECTION 13 — Final Verdict

The Network Recon Engine is a well-governed, genuinely safety-conscious tool whose **process maturity currently exceeds its product maturity**. Its field-evidence loop, decision register, and adversarial review are exemplary for a project of this size; the portable distribution and ArubaOS-CX profile are real operational wins.

But measured against its own objective, the default user journey today **cannot produce a complete infrastructure package on the one platform it has validated**: identity detection and platform-aware selection are bypassed by default recursion, topology discovery parses no neighbors on the field-proven platform, and the health score reports perfection while doing so. These are not speculative risks — each is demonstrated by artifacts this review re-verified.

The next increment of value is therefore not a new vendor, profile, or feature. It is: **make the default path detect, select, discover, and warn loudly; make builds attributable; and obtain one real two-hop topology**. Do those three, and the project's excellent process starts compounding on a product that actually works; skip them, and the evidence loop will keep consuming itself.

**Recommendation: proceed, but gate all future field testing on the Section 10 items 1–3. No new capability phases until the default path is proven on hardware.**

### 14.2 Commands NOT implemented — blocked by functional limitations

**L1 — No per-interface targeting.** Profiles are static, device-global command lists; there is no mechanism to discover interfaces and template commands against them. Excluded high-value commands:
- ArubaOS-CX `show interface <id>` — the only confirmed counters/errors source on CX; the global form is unverifiable (bare `show interfaces` was field-rejected: "Invalid input: interfaces").
- Aruba AOS-Switch `show interfaces <id>` — per-interface counters detail.
- FortiOS `get hardware nic <port>` — per-port NIC error counters.
- Cisco `show interfaces <id> counters` — targeted counter deep-dive.

_Unlock requires: an interface-selection/templating layer in the collection engine (architectural change, needs DDR)._

**L2 — Read-only verb-family safety model.** `READ_ONLY_PREFIXES` is verb-granular by construction; whole verb families are excluded because they contain operational subcommands:
- FortiOS `diagnose lldp neighbors` — the only CLI path to FortiGate LLDP neighbour visibility. Excluded because `diagnose` also carries `diagnose sys kill` and similar; `execute` likewise (`execute factoryreset`, `execute reboot`). FortiGate neighbour loss is therefore diagnosable by link state only.

_Unlock requires: subcommand-level allowlisting inside `validate_read_only_command()` (architectural change; safety-critical DDR with independent review)._

**L3 — Unverified platform syntax (DD-013: exclude when uncertain).**
- ArubaOS-CX `show interfaces counters` (global counters) — existence never confirmed; field research item: execute once against a reachable CX device and record the parser response as evidence.
- ArubaOS-CX `show lag` / `show lacp aggregate` — LACP visibility, syntax unverified in this session.
- ArubaOS-CX OSPF adjacency (`show ospfv2 neighbors`) — syntax unverified.
- Junos `show bridge learning-table` (MX bridging) — EVPN-edge case; would error on standard MX routing instances. The unified Juniper profile cannot carry EX/QFX-only commands without a platform split, and platform splitting is blocked by L5.

_Unlock requires: field evidence (DD-013), not documentation alone._

**L4 — No runtime protocol-capability detection.** Protocol-adjacency commands cannot be included unconditionally because they produce parser errors on devices not running the protocol, polluting `failed_commands`:
- `show ip ospf neighbor` (IOS/IOS-XE), `show ip ospf neighbors` (NX-OS), `show ospf neighbor` (Junos), `show ip bgp summary`, AOS-CX OSPF/BGP equivalents.

This was explicitly deferred in the PHASE-047 decision (candidate "runtime capability detection and command fallback"). _Unlock requires: conditional/profile-branching capability detection (deferred DDR workstream)._

**L5 — Detection layer cannot separate platforms within a vendor.** The single `juniper` profile serves EX/QFX/MX because `detector.py` emits no platform distinction; platform-conditional commands (e.g. EX-only `show ethernet-switching table`) are accepted only as a recorded-rejection hazard on MX, not silently avoided. Same constraint gates any future IOS vs IOS-XE split. _Unlock requires: detector.py platform emission + rule-table entries (the rule table added this session is ready for it)._

**L6 — Single-pass collection, no temporal sampling.** MAC-flap *rates* and broadcast-storm *rates* require repeated sampling (`show mac address-table count` twice with an interval, counter deltas over time). NRE executes each command exactly once. Flap/storm diagnosis therefore relies on device-side logs and cumulative counters (covered by the implemented set) rather than measured deltas. _Unlock requires: collection-loop re-sampling support (architectural change)._

**L7 — Deliberately deferred (value judgement, not a limitation).**
- `show storm-control` (Cisco IOS/IOS-XE/NX-OS): tier-2; interface broadcast counters (now in profiles) carry the storm diagnosis. Revisit if field evidence shows storm-control state changing conclusions.
- FortiGate loop/MAC-flap/broadcast-storm classes: N/A by design — FortiGate interfaces are routed; no switched fabric to loop.

### 14.3 Interaction warning

Every item in 14.1 delivers its full value **only on the flat collection path** until the Section 8 root cause (identity detection skipped on recursive/parallel paths; `parallel_collector` omits `platform`) is fixed. On the default recursive journey today, these new commands still will not be selected for platform-detected devices. Fix order matters: default-path identity → then this delta compounds.
